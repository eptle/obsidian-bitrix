# Классификация видов тестирования
Классификация помогает:
- упорядочивать знания
- ускорять процессы планирования
- оптимизировать трудозатраты
# По запуску кода на исполнение
## Статическое тестирование
Выполняется без запуска кода на исполнение
Ему подвергаются:
- Документы (архитектура ПО, схемы БД)
- Графические прототипы (эскизы UI)
- Код приложения (часто выполняется разрабами при код ревью)
## Динамическое тестирование
Выполняется с запуском кода на исполнение. Запускаться может весь код, либо его части. Проверяется реальное поведение программы.
# По уровню детализации приложения
## Модульное тестирование
Направлено на проверку отдельных частей/модулей программы, которые можно проверить изолированно от других частей. Благодаря нему легче искать дефекты, но оно более затратно по времени и ресурсам.

Бывает восходящим и нисходящим
### Нисходящее
![[Pasted image 20241115212631.png]]
Пишем заглушки для A и B, имитирующие другие модули и тестируем. Далее спускаемся ниже и аналогично тестируем другие модули: C, D, E, F
### Восходящее
![[Pasted image 20241115212850.png]]
Тестируем независимые от других модулей модули E и F, затем зависимое от них D и так далее. Драйвер C пишется, чтобы мы могли в него вставить тестовые данные и отоброжать выходные данные тестирования.
## Интеграционное тестирование
Направлено на проверку взаимодействия нескольких частей приложения, каждое из которых было уже проверено на модульном тестировании. Интеграционное тестирование помогает выявлять ошибки на стыке двух модулей. Если мы пропустили модульное тестирование, то локализовать дефект будет сложнее.
## Системное тестирование
Направлено на проверку всего приложения как единого целого. Помогает взаимодействовать с ПО так, как это бы делал конечный пользователь.
## Приёмочное тестирование
Происходит при переходе приложения из режима тестирования в эксплуатацию. Кроме проверки новых фич мы также тестируем, чтобы ничего не сломалось. При1мные тесты выполняются в режиме, приближенном к реальному использованию.

У тестировщика есть доступ ко всей внутренней структуре и коду продукта и есть знания, чтобы  +- все понимать. Большая точность при поиске ошибок в коде.

| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Показывает скрытые проблемы и упрощает их диагностику                                                | Может выполняться только тестировщиками, обладающими навыками программирования                                             |
| Допускает простую автоматизацию тест-кейсов и их выполнение на самых ранних стадиях развития проекта | Тестирование сфокусировано на реализованной функциональности, что повышает вероятность пропуска нереализованных требований |
| Стимулирует разработчиков к написанию качественного кода                                             | Поведение приложения исследуется в отрыве от реальной среды выполнения и не учитывает её влияние                           |
|                                                                                                      | Поведение приложения исследуется в отрыве от реальных пользовательских сценариев                                           |

## Метод черного ящика
Об объекте тестирования неизвестно ничего (неизвестны внутренности продукта), кроме спецификаций и какой-либо документации/иинструкции, требований. Оказывает воздействие на приложение так же, как это делает конечный пользователь. Иногда называют тестированием на основе неявных требований.

| Pros                                                                        | Cons                                                                               |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Тестировщик может не обладать знаниями в области программирования           | Возможно повторение части тест-кейсов, уже выполненных разработчиками              |
| ПО исследуется в контексте реальной среды выполнения и учитывает её влияние | Часть возможных вариантов поведения приложения может остаться непротестированной   |
| ПО исследуется в контексте реальных пользовательских сценариев              | Для разработки эффективных тест-кейсов необходима качественная документация        |
| Тест-кейсы можно создавать уже на стадии появления стабильных требований    | Диагностика обнаруженных дефектов более сложна по сравнению с методом белого ящика |
| Процесс создания тест-кейсов позволяет выявить дефекты в требованиях        |                                                                                    |

## Метод серого ящика
Комбинация друх вышеперечисленных методов в разных частях приложения.
# Виды тестирования, связанные с изменениями
После устранения дефектов ПО необходимо тестировать заново, чтобы проверить на наличие новых дефектов. 
- Дымовое тестирование -- проверка ключевых частей приложения. Смоук-тесты самые важные и их проходимость должна составлять 100%. Если не пройдено это тестирование, то дальнейшее тестирование бесполезно.
- Регрессионное тестирование -- проверка того, что в том, что раньше работало, не сломалось, т.к. исправление одного дефекта может поломать другие части программы.
- Санитарное тестирование -- используется для того, чтобы доказать и показать работоспособность конкретной функции приложения. Обычно проводится вручную.

Разницы между дымсговном и дурка-тестированием:

| Дымовое тестирование                                                                                                     | Санитарное тестирование                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| Выполняется на начальных сборках программного продукта перед регрессионным тестированием                                 | Проводится на сборках, которые успешно прошли дымовые испытания и перед циклом регрессионного тестирования                           |
| Тестируемая сборка может быть стабильной или нестабильной                                                                | Тестируемая сборка относительно стабильна                                                                                            |
| Мотивом является проверка стабильности новой собранной версии продукта в целом                                           | Основной целью является проверка рациональности системы в деталях, чтобы приступить к более тщательному тестированию                 |
| Включает документацию и работу по сценариям                                                                              | Не делает акцента на какой-либо документации и работу по сценариям                                                                   |
| Можно рассматривать как общий вид тестирования, поверхностно покрывающий все основные функции без глубокого тестирования | Специализированная или более детально ориентированная методика тестирования, направлена на определенную функциональность или функцию |
| Может быть выполнено как автотестами, так и вручную                                                                      | Обычно выполняется вручную                                                                                                           |
| Экономит усилия команды тестировщиков и минимизирует время работы над дефектной сборкой программного обеспечения         | Сохраняет время в условиях, когда его недостаточно для максимально обширного регрессионного тестирования                             |
# По степени автоматизации

Тестирование без использования к.-л. средств автоматизации. Требует усидчивости, креативности, внимания, понимания процесса работы приложения.

## Полуавтоматизированное тестирование
Для некоторых моментов тестирования создаются скрипты.
## Автоматизированное тестирование
Набор инструментов и стредств, позволяющих исключить человека из процесса тестирования в некоторых моментах. Автоматизировать можно как функциональные, так и не функциональные тесты. Например, можно автоматизировать код ревью.

| Pros                                                                                                                                                 | Cons                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Скорость выполнения тест-кейсов может в разы и на порядки превосходить возможности человека                                                          | Необходим высококвалифицированный персонал                                                                                            |
| Отсутствие влияния человеческого фактора в процессе выполнения тест-кейсов (усталости, невнимательности и т.д.)                                      | Высокие затраты на сложные средства автоматизации, разработку и сопровождение кода тест-кейсов                                        |
| Минимизация затрат при многократном выполнении тест-кейсов                                                                                           | В случае ощутимого изменения требований, переработки интерфейсов многие тест-кейсы теряют свою актуальность и нуждаются в переработке |
| Способность средств автоматизации выполнить тест-кейсы, в принципе непосильные для человека в силу своей сложности, скорости или иных факторов       |                                                                                                                                       |
| Способность средств автоматизации собирать, сохранять, анализировать, агрегировать данные и представлять их в удобной для восприятия человеком форме |                                                                                                                                       |
# По принципам работы с приложением
![[Pasted image 20241115222324.png]]
## Позитивное тестирование
Направлено на исследование работы приложения в ситуациях, когда все действия строго по инструкции, без ошибок, отклонений, ввода неверных данных. Если приложение работает неверно даже в таких идеальных условиях, то запахло говном. 

Для ускорения можно комбинировать позитивные тест-кейсы. Например, перед отправкой формы заполнить все поля формы и отправить, а не по отдельности. Это экономит время в стучае удачи, но усложняет поиск ошибки.
## Негативное тестирование
НАправлено на исследования работы при вводе заведомо некорректных данных, тестирование в непредусмотренных сценариях, которые могут привести к потенциальным ошибкам. Негативных тест-кейсов гораздо больше, чем позитивных. Их нельзя объединять, т.к. можно пропустить дефекты.

# По объектам тестирования
## Функциональные
Проводится на проверку соответствий функциональных требований ПО к его реальным характеристикам. Могут быть представлены на всех [[#По уровню детализации приложения|уровнях тестирования]].
## Нефункциональные
Имеется в виду, как именно работает система. Например, тестирование внешнего вида, верстки приложения. Соответствие дизайна макетов и конечного продукта.
# Тестирование производительности
Один из видов [[#Нефункциональные|нефункционального тестирования]]. Это исследование показателя скорости реакции приложения на какие-то внешние воздействия при различной по характеру интенсивности нагрузки.
## Нагрузочное тестирование 
Тестирование способности приложения сохранять параметры и показатели качества при нагрузке в рамках допустимых, либо немного их превышающих, для определения запаса прочности.

Например, количество одновременных пользователей, запросов, чего-либо еще.

Позволяет ответить на следующие вопросы:
- Справится ли система с ожидаемым уровнем нагрузки?
- Держит ли она целевую нагрузку?
- Какие есть узкие места архитектуры?
- Справится ли система с увеличенной нагрузкой? (Применимо к интернет-магазинам в период распродаж и праздников, а также к финтеху)
## Стрессовое тестирование 
Исследование работы приложения при нештатных изменениях нагрузки.

Позволяет ответить на следующие вопросы:
- Выдержит ли наша система резкое увеличение нагрузки?
- Настало ли время для накопления ресурсов для дальнейшего развития проекта?
- Какую максимальную нагрузку выжердит проект при требуемом уровне качества?
- Как быстро система восстановится после резкого всплеска нагрузки?
- Как скажется на стабильности системы отказ каких-либо компонентов? 
## Тестирование стабильности 
Долгосрочное тестирование системы под ожидаемой нагрузкой. Понять стабильность системы в долгосроке. 

Позволяет ответить на следующие вопросы:
- Как меняются характеристики производительности с течением времени? 
- Какое время наработки на отказ при разных уровнях стабильной нагрузки?
## Объемное тестирование
Исследование производительности приложения при обработке больших объемов данных. (В основном касается тестирования нагрузки на БД).

Позволяет ответить на следующие вопросы:
- Как меняется производительность при увеличении объема обрабатываемых данных?
- Какой максимальный объем данных может иметь система для работы на приемлемом уровне качества?
# По привлечению конечных пользователей
## α-тестирование
Выполняется внутри организации-разработчика. Может быть формой внутреннего [[#Приёмочное тестирование|приемочного тестирования]].
## β-тестирование
Выполняется вне организации-разработчика. Активно привлекаются конечные пользователи или заказчики. Может являться формной внешнего [[#Приёмочное тестирование|приемочного тестирования]]. Иначе говоря, продукт достаточно стабилен, чтобы показывать его пользователям, но все еще нуждается в доработке и обратной связи.

Существуют открытые и закрытые бета-тесты. В закрытых некоторая часть пользователей получает доступ к новым фичам, которые еще в разработке и не очень стабильны. Помогают для фидбека, чтобы в открытое бета тестирование попали уже исправленные фичи.
